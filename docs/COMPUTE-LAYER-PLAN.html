The architecture — one idea

IRC / Ergo — presence, channels, backlog, SASL identity ← the SOCIAL / GOVERNANCE plane (humans, on the tailnet) │ friend types !models / !ask qwen3-30b "…" / !lend ▼ the bot — thin bridge: parse command, read speaker's SASL ← the GATEWAY (new; the only thing to build) │ account, enforce allow-list + rate, call the back end ▼ HEARTH / mechnet — model endpoints, caller-profiles, ← the GOVERNED COMPUTE plane (already exists) scheduling/tenancy, the ledger (provenance for free) ▼ your B70s (120B :8082, mesh-llm, oxen) · a friend's lent API key · a lent remote agent

This is your existing three-plane doctrine (sense / act / HEARTH-boundary) with IRC as the human-facing plane. The bot is deliberately dumb — it never decides constraints, it delegates them to HEARTH (keeps the governor deterministic; the bot is hands, not judge).

Paths forward — phased

Phase 0 — decisions (no code)

  • Join model for friends: tailnet invite (recommended — matches the current tailnet-restricted posture & ADR-0014) vs Funnel.
  • Bot language/host: Python on OMEN (recommended) — it can import the HEARTH client in-process, so "route through HEARTH" is a function call, not a new network hop. (Node would reuse The Lounge's ecosystem; Go for a single static binary.)
  • Where the model allow-list lives: reuse hearth/etc/backends.toml or a new bot-side registry with per-model constraints.

Phase 1 — thin slice: read-only bot (proves the loop, zero new infra)

  • Python bot connects to Ergo as a bot user, listens in #general.
  • !models → prints the allowed selection. !ask <model> <prompt> → calls the already-running 120B at :8082 (and any loaded endpoint), posts the answer back.
  • Per-user rate limit in the bot; long output → chunk or paste-link (IRC's 512-byte line limit). ⚠ reasoning-model gotcha: gpt-oss-120b needs a generous max-output budget or it returns empty content.
  • Deliverable proof: a friend in the channel asks a question → it runs on your B70s → answer returns. No card downtime, no new services.

Phase 2 — governed: route through HEARTH

  • Every request goes through a HEARTH caller-profile keyed to the speaker's IRC SASL account → constraints + ledger provenance for free (centralized-capture doctrine holds).
  • Scheduling integration: a model that needs the B70s queues a window via the scheduler instead of preempting the resident tenant — "available now" (only loaded models) vs !request (job-shop queue).

Phase 3 — pooled contribution

  • Lend-a-key provider registry (custody, revocation, per-lender quota).
  • The bot ALSO exposes the pool as an OpenAI-compatible endpoint → a member's Buzz agent or any harness can consume the community pool directly. converges with the Buzz thread (Buzz agents consume Provider+Model — this becomes that provider).

Research / open questions

  1. R1IRC identity → HEARTH caller: confirm Ergo surfaces the authenticated SASL account to a bot (IRCv3 account-tag / WHOX) so the bot can map speaker → profile. Almost certainly yes (Ergo has strong IRCv3 support) — verify.
  2. R2Model registry schema: reuse backends.toml or new? Per-model constraints — max tokens, which cards, schedulable-or-loaded, per-user quota.
  3. R3Key custody for lending: encrypted store, DM/web intake (never in-channel), revocation. Does HEARTH's authority-domain model already express a "lent provider" (caller-scoped authority)?
  4. R4Scheduling UX: "available now" list vs queued windows; how the bot reflects tenancy state (is the 120B up? is a card free?) back into the channel.
  5. R5Output handling: IRC line limits — chunk vs paste-service vs render in The Lounge; streaming tokens vs single post.
  6. R6Abuse/safety: the bot is a new semi-external surface → deny-by-default like HEARTH callers; rate/quota per account; content boundaries for a shared channel.
  7. R7Bot framework: Python pydle/irc/bottom vs Node irc-framework vs Go girc — pick for in-process HEARTH access + IRCv3 support.

Recommendation

Build Phase 1 first — a Python bot on OMEN, !models / !ask, against the live 120B, tailnet-only, one close friend invited. It proves the entire loop (friend in channel → asks → runs on your B70s → answer back) with zero new infra and no card downtime. Governance, lending, and scheduling all layer cleanly onto a working loop — don't build them until the loop breathes. This is the same "thinnest end-to-end slice as a perception instrument" discipline that just paid off on the Buzz thread.
